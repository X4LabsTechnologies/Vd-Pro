# Railway deployment for Vd-Pro

## Deployment files

This repository includes `railway.json`, `Dockerfile`, and `.dockerignore`. Railway builds the Dockerfile, runs `node server.js`, and checks `/api/v1/health`.

## Required Railway services

Create the Vd-Pro service and a Redis service in the same Railway project. Use an external MongoDB connection or a separately managed MongoDB service. The API and the current Bull worker start from the same Node process; do not add a second worker replica until duplicate processing and memory usage have been verified.

## Required environment variables

Set these in Railway Variables. Never commit their real values.

```text
NODE_ENV=production
LOG_LEVEL=info
JWT_SECRET=<long random secret, at least 32 characters>
MONGODB_URL=<MongoDB connection string>
REDIS_URL=<Railway Redis connection URL>
TMDB_API_KEY=<TMDB API key>
WIDEVINE_CDM_URL=<authorized external CDM endpoint, if used>
WIDEVINE_CDM_SECRET=<matching secret, if used>
WIDEVINE_TIMEOUT_MS=20000
```

`REDIS_URL` must be the connection URL generated by the Railway Redis service. Use the Railway reference variable or copy the generated URL; do not use `localhost` in production. If the generated URL is TLS-enabled, keep the `rediss://` scheme.

## Optional environment variables

`BRAVE_SEARCH_API_KEY` is recommended for production search. It adds an independent web index and runs alongside DDG/Bing; it does not replace the existing providers. Create the key in the Brave Search API dashboard and store it only as a Railway secret variable.

Do not set `MONGODB_URL=localhost` or `REDIS_URL=redis://localhost:6379` on Railway. Do not expose `JWT_SECRET`, `WIDEVINE_CDM_SECRET`, or `MEDIAFLOW_PROXY_PASSWORD` in logs, URLs, screenshots, or client responses.

## Recommended service settings

Start with one replica, one worker process, and at least 2 GB RAM for the Playwright browser. Increase memory before increasing concurrency. Keep API and Redis in the same Railway region where possible. Enable automatic restart on failure. Use `/api/v1/health` as the healthcheck and only consider the service ready when it reports `redis: ready`, `mongodb: connected`, and the required integrations as configured.

## Verification sequence

1. Deploy from the intended GitHub branch.
2. Confirm the image build completes and Chromium starts.
3. Confirm `/api/v1/health` reports `ready: true` and `redis: ready`.
4. Test authentication and a search-only request.
5. Test direct extraction using a page for which you have permission to access.
6. Test search plus extraction and inspect the Job state, `validated`, `mediaRequests`, `mediaCandidates`, and `errorCode`.
7. Keep Render available until Railway passes repeated tests.

Railway can provide a better service layout, but it cannot guarantee access to every third-party website. Cloud IP blocking, Cloudflare, DRM, login requirements, changing HTML, and unavailable public media can still cause honest extraction failures.
